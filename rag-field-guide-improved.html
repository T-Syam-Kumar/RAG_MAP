02

Stage by stage

Expand each stage for the decisions that actually move quality. high leverage marks stages where getting it wrong quietly sinks the whole system. Collapsed, this is your revision list.

1 · Ingest & parse+

Turn heterogeneous source formats into clean, structured text before anything else happens — errors here compound through the whole pipeline.

  • Layout-aware parsing for PDFs (tables, multi-column, headers/footers) beats naive text extraction — use a document-structure parser, not raw pdftotext.
  • Preserve structure as metadata: section titles, page numbers, source URL, doc version, timestamps — you'll need these for filtering and citations later.
  • OCR quality gates matter for scanned docs; garbage in is garbage retrieved.
  • Deduplicate near-identical documents before indexing — they crowd out diverse results.

2 · Chunking highest leverage+

The single highest-leverage decision in the whole system. Bad chunks can't be fixed by a better model downstream.

  • Fixed-size: simplest, worst semantic coherence. Fine as a baseline only.
  • Recursive / structure-aware: split on headings → paragraphs → sentences, respecting document structure. Good default.
  • Semantic chunking: split where embedding similarity between adjacent sentences drops — coherent but more expensive to build.
  • Parent-child (small-to-big): embed small chunks for precise retrieval, but return the larger parent chunk/section to the LLM for full context. Usually the best quality-to-effort ratio.
  • Sizing heuristic: 256–512 tokens per chunk with 10–20% overlap is a reasonable starting point; tune against your own eval set, not this number.
WATCH OUTChunking mid-sentence or mid-table breaks meaning. Always chunk on structural boundaries when the source has them.
3 · Embedding+

Converts chunks into vectors that capture semantic meaning. Model choice trades off quality, cost, latency, and dimensionality.

  • General-purpose: OpenAI text-embedding-3, Voyage AI, Cohere Embed, Google Gemini embeddings.
  • Open-source / self-hosted: BGE, E5, GTE, Nomic Embed — check the MTEB leaderboard for your domain and language.
  • Domain-specific beats general-purpose when you have the data: legal, medical, and code embeddings exist and materially help.
  • Match the embedding model to your query type — asymmetric models (short query → long passage) differ from symmetric ones (similar-length texts).
  • Re-embedding cost is real: changing embedding models means re-indexing everything. Pick deliberately.
4 · Indexing / vector store+

Where vectors live and how they're searched at scale.

  • ANN algorithms: HNSW (fast, memory-hungry, most common default), IVF/IVF-PQ (compressed, cheaper at huge scale, small recall trade-off), ScaNN.
  • Managed: Pinecone, Weaviate Cloud, Qdrant Cloud, MongoDB Atlas Vector Search.
  • Self-hosted / embedded: pgvector (if you're already on Postgres), Qdrant, Weaviate, Milvus, Chroma (prototyping).
  • Store metadata alongside vectors for filtered search (by date, source, permission level) — pure vector search without filters doesn't scale to real access-control needs.
  • Plan for updates: incremental upsert vs. full reindex changes your infra choice.
5 · Query processing+

Raw user queries are often bad retrieval queries — short, ambiguous, or missing the vocabulary that appears in your documents.

  • Query rewriting: expand abbreviations, resolve conversational context ("it", "that") before retrieval.
  • HyDE (Hypothetical Document Embeddings): have the LLM draft a hypothetical answer first, embed that instead of the raw query — often closer to the target passages.
  • Decomposition: break multi-part questions into sub-queries, retrieve for each, then synthesize.
  • Routing: classify the query to pick the right index/tool (structured DB vs. document search vs. web) before retrieving anything.
6 · Retrieval high leverage+
  • Dense (vector) retrieval: good at semantic/paraphrase matches, weak on exact terms — IDs, product codes, rare proper nouns.
  • Sparse (BM25/keyword): strong on exact-term and rare-word matches, no semantic understanding.
  • Hybrid: run both, combine scores — usually the strongest general-purpose default. Combine via weighted sum or Reciprocal Rank Fusion (RRF).
  • Retrieve more than you need (top 20–50) before reranking narrows it down — recall first, precision second.
7 · Reranking best ROI+

A cross-encoder scores (query, chunk) pairs jointly — slower than the bi-encoder used for initial retrieval, but far more accurate, so it's used only on the shortlist.

  • Cohere Rerank, BGE-reranker, ColBERT-style late-interaction models.
  • Typical pattern: retrieve top 30–50 → rerank → keep top 3–8 for the prompt.
  • This step alone is often the single highest-ROI addition to a mediocre RAG system.
8 · Generation+
  • "Lost in the middle": models attend more reliably to the start and end of a long context — put the most relevant chunk first or last, not buried in the center.
  • Instruct the model explicitly to answer only from provided context and to say when it doesn't know — this reduces but doesn't eliminate hallucination.
  • Ask for inline citations (chunk IDs or source markers) so answers are traceable and verifiable.
  • Watch your context budget: more chunks isn't always better past a point — irrelevant context dilutes attention and cost.
9 · Guardrails & citation+
  • Post-hoc groundedness check: verify the generated claim is actually supported by the retrieved context before returning it.
  • Filter for PII leakage, toxic content, and off-policy topics before the response reaches the user.
  • Return source citations/links so users can verify — this is also your fastest debugging signal in production.
  • Define a fallback: what the system says when retrieval confidence is low, rather than confidently answering from nothing.

04

Advanced RAG patterns

Reach for these once naive retrieve-then-generate stops being good enough.

Self-RAG / Corrective RAG (CRAG)+

The model critiques its own retrieved context, decides whether it's sufficient, and re-retrieves or falls back to a different source (e.g. web search) if not — adds robustness at the cost of extra latency.

Agentic RAG+

The LLM acts as an agent that plans which tools/indexes to query, in what order, iterating over multiple retrieval steps rather than one fixed pass — needed for multi-hop or comparison questions across sources.

GraphRAG+

Builds a knowledge graph of entities and relationships from the corpus, then retrieves via graph traversal alongside or instead of vector search — strong for questions requiring relational or multi-hop reasoning across many documents ("how are X and Y connected").

Multi-hop / iterative retrieval+

Retrieve, read, generate a follow-up query based on what's still missing, retrieve again — needed when one query can't surface everything the answer requires.

Reciprocal Rank Fusion (RRF)+

A simple, robust way to merge ranked lists from dense and sparse retrieval without needing to calibrate score scales — sums 1/(k + rank) across lists per document.

Contextual compression+

After retrieval, strip irrelevant sentences from each chunk before it hits the prompt — shrinks context, cuts cost, and reduces the "lost in the middle" problem.

Contextual retrieval (chunk-level context prefixing)+

Prepend a short LLM-generated summary of where a chunk sits in the larger document before embedding it — fixes chunks that are meaningless in isolation (e.g. "the company reported 10% growth" with no antecedent).

Query routing / semantic caching+

Route queries to specialized indexes (FAQ, code, tickets) instead of one giant index; cache semantically similar past queries and their answers to skip the pipeline entirely on repeats.

05

Getting to production

A prototype that works on 10 hand-picked questions is not a production system. This is what closes the gap — high impact items marked.

  • Freshness pipeline: automated re-indexing on document change, not manual reruns — with versioning so stale chunks don't linger.
  • Access control: retrieval respects document-level permissions (RBAC) — never let vector search surface content a user shouldn't see.
  • Observability: log every query, retrieved chunks, and final answer with trace IDs — you can't debug a bad answer you can't replay.
  • Semantic + exact caching: cache embeddings, frequent queries, and even full answers where safe — the biggest cost lever after model choice.
  • Fallback behavior: defined, tested response for low-confidence retrieval — "I don't know" beats a confident wrong answer.
  • Guardrails on both ends: input filtering (prompt injection via retrieved documents is a real attack surface) and output filtering (PII, toxicity, groundedness).
  • A/B / shadow testing: new chunking strategies, embedding models, or prompts get evaluated against the fixed eval set before rollout, then shadow-tested on live traffic.
  • Cost budget per query: know your embedding, retrieval, rerank, and generation cost breakdown — reranking and long contexts are the usual surprise.
  • Rate limiting & backpressure: vector DB and LLM API both have limits; queue and degrade gracefully rather than failing hard.
  • Continuous eval: the eval set and metrics from §03 run on every change, not just at launch — corpora and query patterns drift.
PROMPT INJECTION VIA RETRIEVALRetrieved documents are untrusted input. A malicious or compromised document can contain instructions aimed at the LLM ("ignore previous instructions..."). Treat retrieved content as data, never as instructions, and sanitize/monitor for this pattern.
06

Common pitfalls

The failure modes that show up in almost every RAG system at least once, ranked by how often they're the actual root cause.

Chunks too large or too small
MOST COMMON
Too large dilutes relevance signal and wastes context; too small loses meaning. Fix: parent-child chunking — small chunks for search, larger parents for context.
No eval set, tuning by vibes
MOST COMMON
Every change looks like an improvement on the three examples you eyeballed. Fix: build a fixed 50–200 question eval set early.
No hybrid search
COMMON
Pure dense retrieval misses exact IDs, codes, and rare terms. Fix: add BM25 and fuse with RRF.
Optimizing generation while retrieval is broken
COMMON
A better prompt can't fix wrong context. Fix: measure retrieval metrics in isolation before touching the prompt.
Stale index
COMMON
Documents change, the index doesn't. Fix: automated, event-driven re-indexing with freshness monitoring.
Treating retrieved text as trusted instructions
HIGH SEVERITY
Opens the door to prompt injection from within your own corpus. Fix: clearly delimit retrieved content as data in the prompt template.
No citations in the answer
EASY FIX
Unverifiable answers erode trust and make debugging nearly impossible. Fix: require inline source citations by default.
